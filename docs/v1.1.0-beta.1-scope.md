# Proposed v1.1.0-beta.1 scope

This is a preparation document, not a release announcement. It neither changes
the crate version nor creates a tag, GitHub release, or new compatibility
promise. A future `v1.1.0-beta.1` remains an explicit owner decision after its
then-current commit has passed the release criteria below.

## Version spaces

The current checked-in values remain unchanged:

| Space | Current value | Beta implication |
| --- | --- | --- |
| Package/release | `1.0.0` | A future beta may use `1.1.0-beta.1` without changing the other spaces automatically. |
| Public API | `1.0.0` | Remains `1.0.0` while the transport-neutral contract is compatible; native diagnostics are not a `PublicEngine` capability. |
| On-disk format | V4 | Remains V4 unless a separately designed persistent-format change requires V5. |
| Readable formats | V1--V4 | Must remain V1--V4, including the Java-generated V1 fixture. |

The diagnostics added after v1.0.0 are in-memory and handle-local. They do not
need a new on-disk format or a database migration.

## Candidate scope since v1.0.0

A future beta release note can accurately describe these implemented native
engine additions, subject to its final qualification run:

- transaction snapshot-version visibility and atomically staged numeric
  increment/decrement operations;
- native `Transaction::compare_and_set` evaluated against a transaction's
  staged view, with established transaction-batch recovery behavior;
- opt-in, non-persistent optimization diagnostics for reads, writes, scans,
  indexes, CAS attempts, and bounded hot-document observations;
- explainable index, hot-document, and CAS-contention recommendations;
- bounded workload profiles, evidence-bearing candidates, qualitative
  benefit/cost/confidence, and read-only simulations;
- explicit preceding/current workload windows, deterministic count-backed drift
  detection, and candidate/simulation re-evaluation that can label old
  evidence stale or invalidated.

These are native diagnostic and engine extensions. They do not change the
stable API-major promise into a server protocol or an autonomous optimizer.

## Explicit non-features

The candidate beta must continue to state that it does **not** provide:

- multi-writer commit, field-level conflicts, or serializable isolation;
- automatic optimization, index creation, storage-plan activation, migration,
  verification, or rollback;
- durable request-id deduplication/idempotency;
- clusters, replication, sharding, consensus, distributed transactions,
  admission control, or shard-per-core execution;
- a WiredTiger integration, external database dependency, or ML optimizer.

## Beta release gate

Before an explicit tag/release decision, the exact candidate commit must have:

1. successful Linux and Windows CI;
2. all tests, `cargo fmt --check`, `git diff --check`, both configured Clippy
   modes, the process-crash harness, and the release build green;
3. a clean worktree with `main` equal to `origin/main`;
4. no unreviewed dependency additions and no `unsafe` code;
5. V1--V4 compatibility and the Java V1 fixture passing in that exact run;
6. an unchanged `v1.0.0` tag;
7. final release notes that state the implemented scope and known limits above.

Passing these checks prepares a candidate for an owner decision; it does not
create, move, or publish `v1.1.0-beta.1`.
